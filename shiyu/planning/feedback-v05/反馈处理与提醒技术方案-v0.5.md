# 拾语：反馈处理与提醒技术方案 v0.5

2026-11-11，后端／SRE／QA增量稿。只修设计，未开发、接入提醒、创建自动化或发送消息。复用FastAPI、PostgreSQL、Outbox、私有对象存储和Worker；独立Feedback Module，不新增客服微服务体系。用户已决定首版仅应用内提醒；外部渠道留待后续，不启用钉钉／邮件，也不申请操作系统通知权限。

## 1. 需求、对象与Interface

建议R39＝m36提交反馈；R40＝m37本人反馈与进度；R41＝d04管理反馈、提醒与迭代关联，最终ID由产品统一。

| 对象 | 必要事实与约束 |
| --- | --- |
| Feedback | feedback_id、服务端绑定的owner/space、类型、正文、用户选择的上下文引用、客户端版本、提交幂等键和时间 |
| Attachment | 本人主动选择的截图／日志、私有对象引用、扫描／脱敏确认、保留与删除状态 |
| StatusHistory | 状态前后值、操作者角色、理由、时间；追加留痕，不用覆盖记录掩盖投诉 |
| Triage | 用户自报影响、建议优先级、依据／规则版本、人工确认、负责人；AI建议不是最终处置 |
| IssueLink | 聚合问题／需求、关联版本、修复或不采纳说明、复测与原提交关系 |
| InboxNotification | 事件／接收账号或受限管理角色、feedback引用、最小摘要、created_at、read_at、分页游标；事件＋接收人唯一 |
| NotificationDelivery | 应用内投递尝试、回执及失败状态；未来外部渠道Adapter另行启用，不默认产生外发任务 |

小Interface为submit_feedback、get_my_feedback、append_info、triage/assign、change_status、link_issue、list_inbox、mark_read、get_delivery_status。管理动作鉴权并条件写版本，不能任意改其他用户记录或账本。反馈不授予Agent读取材料、外部应用或执行工具的权限。

## 2. 提交、身份与附件

登录用户身份来自服务端认证，不相信请求体owner。用户仅看自己的提交；客服／管理员按角色、空间及处理范围访问，附件读取也核权。游客如首版支持，使用不可枚举的受限回执和独立追踪凭据；不能仅凭反馈编号查正文。游客未做防滥用与找回设计前，不假装拥有完整个人反馈历史。

默认只附页面类型、构建版本、错误码及用户确认的脱敏资源／任务引用，不自动上传原文、音频、完整聊天、截图或设备日志。引用须验证本人归属，客服不会因此自动获得源文件全文权限。

附件由用户选择并预览，可删除后再提交；限制类型、大小、数量和解码资源，扫描后才向有权处理者开放。脱敏日志仅包含必要状态与关联ID，过滤认证头、令牌、签名URL参数和个人内容；自动脱敏不能保证识别全部敏感信息。费用异议只需任务／账单引用，不收集银行卡密码、验证码或原始密钥。保留期、导出删除及备份边界随资产政策明确，不默认为永久保存。

按账号／设备／网络信号分层限流，保护正常投诉，不以重复提交或负面内容自动封禁、删单。正文、附件和链接均是不可信内容，不能成为提示注入或工具授权来源。

## 3. 持久回执与提醒可靠性

提交在同一事务写Feedback、首条StatusHistory和Outbox；幂等重试返回同一反馈编号。**提交成功、提醒送达、开始处理、修复完成分别记录。** 通知失败不回滚已接收反馈，也不能让用户误以为投诉丢失。

Worker按event_id＋recipient去重，将通知和消费回执事务写入持久Inbox，有限退避、失败池和人工核查。反馈创建提醒投给有权管理角色，处理进度提醒只投给本人；读取提醒及其详情时再次校验当前角色和反馈权限，不因历史曾有权限永久可读。应用内反馈待处理列表始终兜底。监控Outbox最老年龄、Inbox投递失败、未分派反馈和长时间未更新状态，不能只监控“请求返回200”。

首版采用服务端read_at记录未读，分页游标用于增量拉取，两者不混用。进入应用、返回前台或打开反馈中心时拉取最新状态；页面保持打开时可用有界轮询刷新，SSE只列候选，连接恢复后仍按游标补拉。拉取不等于阅读，查看详情或主动标记才更新read_at；标记操作幂等，四端读取同一状态，不丢未读提醒。

提醒状态区分“已写入应用内收件箱”“客户端已获取”“用户已读”，不把数据库写入当成用户已看到。应用或页面关闭后，持久提醒会在下次打开时可见；**这不是系统推送，不保证用户离开应用后即时收到通知**。本轮不建后台自动化、不申请系统通知权限，也不发送任何消息。是否能及时处理取决于用户查看和实际责任安排，当前无送达时延或值班SLA。

钉钉／邮件Adapter仅为后续扩展：届时独立确认渠道、接收人、发送账号、权限、费用和数据范围，不自动将旧反馈补发。外发内容只允许最小编号／类别／影响级别及需登录入口，不带投诉全文、附件或直达签名地址；渠道无幂等或结果查询时，另评有限重试与未知处理，不能照搬应用内数据库事务保证。

## 4. 分级、状态与迭代

候选状态：已收到→待补充／待分派→处理中／已纳入计划→已处理→用户确认或重新打开。每次变化可见时间与说明；已处理可表示解决、解释、无法复现或不采纳，不能一律显示“已修复”。修复需关联版本及复测证据；进入迭代计划不等于承诺发布日期。

隐私泄漏、异常收费、账号安全及核心学习不可用标为优先核查候选。AI可归类、摘要、建议相似问题和紧急程度，但不能自动降低投诉级别、关闭投诉、退款、修改账本、公开内容或替用户删除材料。人工确认分派及结论；无人响应时明确待处理，并由既有安全／费用保护阻止相关风险扩大。

聚合相似反馈只建立IssueLink，保留每条原始投诉、提交者及自己的处理记录。管理端按影响人数／严重程度／复现证据／产品目标排序，采纳后关联需求与版本；发布后将结果写回原反馈，用户可确认或重开。提醒、处理时限和责任人按实际资源约定，当前不填虚构SLA。

## 5. 指标与验收

统计反馈数量、有效分类分母、已分派率、首次有效响应时间、解决／解释／不采纳分别计数、重开率、Inbox写入／获取／已读与失败、采纳后版本交付。聚合问题数与提交数分开；不靠自动关单刷解决率，不将所有用户不满都算产品缺陷已确认，也不把未读自动记作无人处理。

验收全部未执行：双账号隔离与伪owner；重复提交同回执；附件不默认上传且越权拒绝；Outbox故障后仍能查反馈；Inbox重复事件不增单、失败可补投；四端read_at一致、分页补拉不漏项、仅拉取不自动已读；应用关闭后下次进入仍有未读且不声称系统推送；AI不能擅关投诉或改账；聚合不丢原始提交；解决关联版本、重新打开及资产删除回执。外部渠道明确未启用，无真实外发验收。本轮不新增底栏栏目，提醒故障不影响学习主线。

进入实现前收口：分类／状态词典、应用内管理角色与接收范围、分级规则、附件和保留政策、投诉人工责任及必要服务授权。首版渠道已决定，不再作为待选择项；外部提醒以后独立评审。本模块不因“方便反馈”扩大Agent权限或默认采集用户材料。
