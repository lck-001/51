# 拾语：后端与数据库架构独立评审 v0.2

日期：2026-11-11。评审者：Codex 独立后端/数据库架构角色。审阅v0.1后端、数据、架构统筹与需求基线，核对官方公开资料；未开发、压测、访问数据库或调用付费服务。本稿不代表真实WorkBuddy或百度搭子意见，也不证明运行容量。

## 1. 结论：保留主路线，但需补运行设计

**保留 Python/FastAPI 模块化核心＋PostgreSQL权威事实/账本＋私有对象存储＋独立Worker。** 它采用成熟、受维护的技术，适合从本人和受邀朋友验证起步。没有证据证明这是整个市场“最主流第一”的组合；组件成熟、设计合理和本项目容量通过是三件事。PostgreSQL任务队列是可行的受限起步方案，不等于完整工作流系统已由数据库自动提供。

可继续选型/需求评审。上线前必须补齐数据库维护与连接预算、外部执行恢复、媒体数据面、备份恢复和容量准入；当前没有不可实现的已证实硬障碍，也没有支持“任意用户规模无缝扩容”的证据。

## 2. 官方事实与本项目含义

| 官方可核对事实 | 对方案的约束 |
| --- | --- |
| PostgreSQL SELECT文档说明SKIP LOCKED可用于多个消费者访问类似队列的表，但会给出不一致视图[1] | 只用于可领取任务候选，不用于余额、权限、完整库存等权威判定；不承诺严格全局FIFO |
| MVCC需要定期VACUUM；高频更新/删除与长事务会影响清理[2] | 心跳/租约/状态频繁变更的任务表需专门维护与保留策略，不能仅加一张队列表即算可靠 |
| max_connections增加会扩大相应资源分配[3] | API横扩和Worker扩容同时消耗连接，不能用无限连接代替容量规划 |
| 流复制通常存在异步延迟，异步故障切换可能丢失已提交事务[4] | 分享撤回、费用准入和授权新执行读权威源；普通只读副本不承担这类准入。HA副本也不能代替备份 |
| PITR依赖可用基础备份和连续WAL，且不能恢复外部世界状态[5] | 需恢复演练，并将对象存储版本、服务请求和账单核查纳入恢复流程；仅数据库恢复成功不是全系统恢复成功 |
| FastAPI进程复制可利用多核，每进程会有自己的内存[6] | API保持轻量无本地权威状态；模型/转码不装进每个API进程，多开进程仍需控制总内存与连接 |
| S3签名URL的有效性在请求开始时检查，已开始下载可能跨过有效期继续[7] | 短URL有效期不是已经传出字节的撤回保证；必须写清新请求、既有流和本地副本的不同边界 |

版本选择要核对官方支持期限、托管商支持及扩展兼容[8]；新项目不选即将结束维护的老版本。17/18可列候选并在实施前确认，不用搜索页“current”推导本项目必须采用的最新版本或固定小版本。

## 3. P0：开发承诺或上线前必须补清

### P0-A：灾后恢复不能导致已付费调用重发

原方案有在线的未知核查，但没有灾后恢复运行手册。数据库恢复到旧时间点，可能丢掉“已向供应商提交”的意图/请求ID，而供应商仍已执行并收费；账本去重键也可能一起回退。fencing_token只限制平台提交，不会撤销外部真实副作用。

建议增加恢复隔离模式：恢复期间停止所有新外部调用、发布和结算；核对恢复时间/数据丢失窗口、独立恢复审计、供应商请求/回调/账单和对象制品版本；不确定步骤挂起核查；对账后分资源池恢复。供应商能接收幂等键时稳定业务操作键不得因进程或恢复变化。不能查询、不能幂等的步骤列为人工核查，不把它们自动重排队。

验收：模拟“供应商已完成、平台提交记录在恢复点之后”及“迟到回调”，恢复后没有未经核查的重复调用；对账项、未知费用与已恢复数据范围可追溯。这是待执行的用例，不是本次实测。

### P0-B：控制面与音视频数据面分开

如果所有视频、录音和原件字节都经FastAPI主进程代理，API带宽、连接数、内存和出站费用可能先于业务CPU耗尽。用户拖动播放会产生Range请求，不能用整文件缓冲下载再转发。

建议API负责身份/版本/范围/下载许可，私有对象存储承担文件，媒体网关或具权限核验的分发层承担字节流。是否上CDN由地域/访问量/成本验证决定，不默认公有缓存。受控上传使用限定对象、用途、大小/校验和及完成确认的短期能力；大文件可分块续传，但接口与过期恢复需前后端共同约定。

可撤回内容分层定义：撤回后拒绝新授权与新读取请求；已经建立的流、已签发许可窗口、客户端缓存、外部副本分别明确。不承诺每传一个字节都查询数据库，也不以一天的签名地址宣称即时撤回。验收覆盖Range/断点、缓存命中、权限变化、新旧连接和失效窗口。

### P0-C：共享数据库的资源准入必须量化

业务事务、任务领取/心跳、Outbox、账本、统计投影共用数据库，是成本较低的起点，也是共同故障域。需先规定各角色最大连接、查询超时、并发、批次和后台资源配额，留维护/应急连接；API与Worker扩容不能各自随意增加连接池。

任务领取仅用短事务，领取后立即提交；外部HTTP、模型等待或转码期间不得持行锁/数据库事务。预算锁按账号或约定额度粒度，避免所有用户争一把全局锁；超限与未知保留规则仍按权威账本执行。重投/租约和任务终态归属仍保留现有设计。

## 5. 容量公式：先算工作量，再谈机器

尚无用户量、视频时长、每题调用和供应商时延数据，不报QPS或“几核支持几万人”。下列用于填写假设：

- 每日步骤数＝活跃用户×每人材料数×每材料平均步骤数＋复习/评测步骤；峰值到达率单列，不能用全天平均替代晚高峰。
- 某资源池在途需求≈到达率λ×平均占用时间W；建议并发还受CPU/内存、供应商并发/速率和预算限制。不是把该乘积直接当满足P99的压测结论。
- 总数据库连接上界≈API实例×每实例进程×每进程池上限(含溢出)＋各Worker/核查/投影池上限＋维护预留。
- 媒体出站带宽≈同时播放人数×平均码率；存储≈每日新增媒体秒×平均码率÷8×保留天数×版本/副本系数，另加原件、索引、WAL与备份。
- 积压清空时间≈积压任务量÷(完成速率−新到达速率)，只有后者为正且任务类别相近时才有意义。

纯假设算例：100人同时播放、每路0.8Mbps，则视频数据面约80Mbps，未含协议与重试；不代表已选视频规格或已测服务器支持100人。相比加API CPU，降低码率、缓存有权内容、独立媒体分发可能更直接；须连费用/撤回策略一起评估。

## 6. 分阶段扩容，不提前堆组件

1. **本人/受邀朋友验证**：模块化API，受控PG任务热表，解析/语言/媒体/评测独立进程和限额；DB与原件可靠备份，基础可观测性、恢复手册和成本告警。若单机部署，明确该故障域与停机代价，不称高可用。
2. **API横扩/Worker横扩**：API无本地权威状态，统一存储/身份/额度；Worker租约/幂等/配额通过故障验证后按资源池增副本。连接预算同步调整。不要盲加Worker突破供应商限额。
3. **媒体与统计分离**：先卸载大字节与重建；必要时增加只读副本/独立分析投影。权限、账本、新执行准入仍读可满足一致性要求的权威路径，不能因为“读写分离”用延迟副本核权。
4. **迁移投递能力**：若任务轮询/热表维护明显挤压OLTP并已完成索引、退避、配额等优化，才评估专用Broker/成熟持久任务实现；DB继续持有业务任务/账本真相。迁移保留稳定任务ID、Outbox、去重和双读/核对计划，避免两条队列同时执行同一付费步骤。
5. **分库/分片**：单写主库成为已测瓶颈、垂直优化和隔离不能满足SLO且收益足以覆盖事务/运维成本时再考虑。先拆只读投影/媒体元数据等可独立域；用户分片会改变预算事务、分享跨用户访问和全局任务调度，不承诺无需改造。

托管Postgres与私有对象存储可减少AI主导研发的部分维护工作，但不自动解决应用幂等、恢复对账、数据地域、删除和账单。具体托管商/规格/HA档位需费用与资源决策，当前不采购。

## 7. 备份、恢复、升级与上线证据

- 定义并由产品确认RPO/RTO目标，按目标选择备份、WAL、HA/副本和演练，而非先声称零丢失。数据库、对象版本、配置/密钥引用、任务意图与账本的恢复关系须有清单；配置和密钥另做受控备份，不假定PITR包含它们。
- 从独立环境实际恢复并核查：账号/版本/词本/成绩、发布权限、删除墓碑、未知外部任务、供应商对账；记录实际恢复点与恢复用时。当前无恢复演练证据。
- 升级使用兼容演进(先扩字段/双版本读取，再切换，再清理)，数据库迁移与应用回滚分开；不能应用回滚却丢失新版本写入。长迁移分批，索引建立和锁影响先验证；重大PG升级单独验证扩展、备份与回退/恢复方案。
- 上线前必须有任务/队列/账本/数据库/媒体/供应商分层指标、告警接收人、处置手册、轮换与定期演练。AI Agent可协助排障，但不能把“Agent在”当值班责任和可用性承诺。
