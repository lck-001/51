# M13 联合评审结论：后台与锁屏播放

2026-11-12。依据本目录产品、架构、独立QA三份评审及当前源码，**方案有条件通过，可进入有限状态详细设计与验证；尚未实现或验证任何新的后台能力。** 本次只更新术语和评审文档，未改运行逻辑、依赖、manifest、系统或设备。

## 一、采纳的规则与设计

1. 播放意图、实际播放、暂停原因、素材/账号归属与会话代际分别记录。UI、系统面板与耳机命令走同一个Playback Module Interface；不直接在多个页面调用Player。命令accepted不等于真实播放，实际状态以引擎/平台回执收敛。
2. 用户主动的音频具备离屏连续播放目标；用户手动暂停必须保持。视频后台默认暂停；显式仅听音、画中画后续独立验收。当前实验统一pause不是该目标的实现。
3. 播放宿主与页面生命期分离，保留现有media_kit引擎；各OS由SystemPlayback Adapter处理会话、焦点与系统控件。没有可靠背景能力的平台应报告仅前台可用，不能用常亮屏幕伪装成功。
4. 采集及预览仍为前台明确启动。采集开始撤销旧播放恢复资格；拒权、停止、保存完成或收起预览不自动恢复播放，更不自动开麦。资源active或unknown时，不接受系统Play来抢占、结束录制或制造外放回录。
5. 短暂系统中断只在同一素材/版本/代际、旧意图未被用户改变、原先确实播放、焦点/安全输出恢复、所有阻断原因清除时，才保留有限恢复资格。耳机断开、永久失焦、新账号/材料、旧事件、进程重启均不能擅自复播。
6. 系统媒体元数据默认通用标题，不发布私人文件名、正文、图片、文件路径或签名URL；OS媒体控制不能成为Agent或其他App启动采集、读取私人目录的入口。媒体通知与反馈/运营提醒分责。

## 二、实现前必须关闭的协议缺口

QA指出当前实验存在串行长调用阻塞后台清理、忙时遗漏系统停止事件、先丢相机引用再释放、清理异常跳过后续步骤、异步启动完成后未复核环境等问题。不能把已产出文件/SDK引用为空当作这些问题已解决。

| 必须固定的契约 | 详细设计应表达 |
| --- | --- |
| 恢复资格撤销 | 用户Pause/Stop、切换素材/账号和采集动作立即使旧恢复资格失效；后续focus/lifecycle不覆盖。结束采集后保留需要新Play的门闩，不能仅删除capture hold就重新播放 |
| 原生事件归属 | 旧进度、完成、错误、系统控件与采集回调须携带或核验所属上下文；执行恢复前重新核验当前事实，不只在入队时判断 |
| 预览与采集资源 | 预览也可能持有输入；inactive/active/stopping/unknown至少能分清。释放不确定时保留可处理信息并拒绝新采集/不安全恢复 |
| 后台与迟到初始化 | 后台到达时立即撤销采集启动资格；不能只把清理排在长await后。初始化/开始回执到达时重查前台和代际，过期成功补偿停止/释放 |
| 清理与文件结果 | stop、保存、预览释放和播放暂停须独立尝试、逐项记录，失败不互相跳过；传感器停止与文件保存成功分别确认。没有零毫秒停采或必保存的承诺 |

## 三、平台选择与未确认能力

Android/iOS/macOS的audio_service、audio_session仅为架构候选，不修改当前pubspec/lock。其公开平台声明不能解释成Windows支持或所有Mac锁屏控制已证实。原生macOS不照搬iOS AVAudioSession；Windows使用现有C++技术栈的窄SMTC Adapter候选。

Android target36受焦点与媒体FGS条件约束；需要的manifest/宿主实现另行审查，不默认增加POST_NOTIFICATIONS，更不能用媒体会话豁免扩大普通通知范围。恢复时若宿主已不存在或OS不允许，不在后台偷偷重建服务。iPhone、原生Mac、Windows睡眠/锁屏与Android不同，必须分开取证。详细官方依据见架构稿。

## 四、下一工作包与准入

下一包限定为：以固定上下文和可控事件，详细设计并验证意图/暂停原因/代际/资源清理状态。测试应从Playback Interface交互，覆盖竞态及未知结果；不靠复写实现内部条件得到假通过。纯状态结果只能证明策略，不证明声音、系统控件、FGS存活或实际关麦。

纯状态与同行复核完成后，再按平台逐项验证原生Adapter；此时才决定依赖/manifest变更并评估回滚。不得跳过QA矩阵直接将生命周期分支删除。Android实机仍待设备阶段，Apple设备后验，专业声学评测未接入；本结论不是完整产品验收、灰度或上线批准。
